Help the user install the private account package, obtain one working private communication service and verify each requested client. The package includes the messaging skill, this onboarding skill and the complete service source, version **0.5.6**, under `assets/service-template/`. It has no shared MCP endpoint. Each owner uses their own Site and database. Explicit user instructions take priority; if they request another hosting or identity design, resolve the source's Sites authentication requirement before deploying.

The manifest designates this skill for onboarding. A host may offer or launch it after installation; do not claim that every Install click automatically runs setup or deploys a server. If onboarding has not started, the user can ask to set up Paprika Messenger. Saving the account package, installing it, publishing a Site, displaying an installation card, connecting a client and enabling recipient notifications are separate milestones.

Explain briefly that messages and routing data are stored in the owner's private service and are not sent to the package publisher. The bundled [privacy notice](../../PRIVACY.md) explains storage and deletion. Setup needs no transcripts, private message histories or pasted authentication secrets.

## Save and install the account package by default

The default request to install or set up Paprika means a PRIVATE account plugin for supported cloud, mobile and desktop clients signed into the same account. Use the hosted account-save workflow before completing default onboarding. A local Codex marketplace entry is a device-only install; do not silently use `codex plugin add` or the local staging helper as a substitute. An explicit local-only request may use that path, with its device scope reported clearly.

1. Discover Plugin Creator's native account creation, metadata/source inspection and update capabilities. Establish the intended authenticated account and scope before saving. For the personal default, use Personal account context; an active workspace makes `create_plugin` save a WORKSPACE plugin. PRIVATE visibility, branding and a cache path do not prove USER scope. If personal context cannot be established, retain account saving as pending and direct the user to select Personal context; do not silently change an existing plugin's scope or audience.
2. Resolve an existing matching account plugin from a verified ID, selected plugin or setup checkpoint. Without an ID in a personal context, use `list_owned_personal_plugins`, following every cursor, and inspect candidates' metadata/source. Reuse the matching owned package and its backend ID, scope and audience. Resolve ambiguous matches before choosing. Canonical Sites service plugins are a separate identity and are not edited with the archive editor.
3. Obtain the complete private account ZIP from this repository's `releases/<plugin-version>/` directory, verify its `SHA256SUMS`, or build it from a complete source checkout with `node scripts/prepare-account-plugin.mjs`. Use the current portable manifest's version. If onboarding was invoked from a local cache, retrieve the complete released package or source; do not upload a partial skill or a service-only template as the account plugin. For creation call Plugin Creator's `create_plugin` with the ZIP's absolute local path as `archive`. For an existing eligible account plugin use its supported update workflow with the same identity and observed release; reuse a current complete matching release without uploading again. Account saving creates no Site and must not bind the publisher's service.
4. Verify the saved backend plugin ID, `plugin_url`, release, actual scope and package version through native metadata/source inspection. The account package and any explicitly selected local package must use the same current manifest version; do not select the old 1.3.4 archive or use the Site connection's independent listing version as the package version. Inspect the stored root manifest and complete resources when updating an older matching package. If backend metadata reports another version or cannot confirm it, reconcile the same eligible package through its supported update workflow and retain version verification as pending instead of claiming it current. Keep these non-secret resume values outside Git with the existing setup checkpoint. Show the returned account plugin link and its supported Install interface. Verify account installation through host installed-plugin status when available; a saved package, displayed link or local cache alone does not confirm installation. If the Install step still needs the user, report it as pending and continue independent checks. Missing account-save tools require discovering/connecting Plugin Creator; retain the ZIP and progress rather than substituting a local install.

An already deployed working private Site is reused while account installation is completed. Its successful publication or another client's connection cannot prove the account setup package is installed or that mobile/cloud clients are ready. Confirm each milestone separately. See the repository's [account installation guide](https://github.com/newbiesitl/paprika-messenger/blob/main/docs/ACCOUNT-PLUGIN.md).

## Check deployment prerequisites before registration

For a new deployment or requested source update, verify Node.js 24 or later, npm for the existing package-lock.json, Git and the selected installed Sites packager’s actual requirements in the same execution environment. Reusing a working authenticated service needs no local build tools. A bundled Node or Git executable does not prove npm or Bash exists. When the installed packager requires Bash and it is missing, use a capable environment or this package’s tested native-tar recovery in [Windows packaging](assets/service-template/docs/WINDOWS-SITES-PACKAGING.md). It retains the installed Sites build validator, manifest attribution, migrations and verified source revision. Never register another Site to repair a missing executable. Resolve missing prerequisites before dependent registration; preserve an already registered Site on recovery.

## Check access and find the right instance

1. Inspect available native capabilities before creating anything. A connected Messenger can be checked with read-only `list_boards` and `list_messages` calls. Sites setup needs native Sites discovery/metadata, registration, runtime-settings and publication capabilities, plus a writable execution environment with Node.js 24 or later. Search available tool/plugin metadata before reporting a missing capability. If Sites is missing or disconnected, discover the eligible Sites integration and show its supported Install/Connect interface; do not guess a plugin ID. If that interface is unavailable, direct the user to enable/connect Sites in the host's Plugins UI. Never silently change workspace administrator controls or treat a permission error as permission to bypass them. Continue independent inspection while a connection is pending; dependent Site operations wait for a real connection. For a restricted workspace or missing execution environment, state the specific prerequisite and retain completed setup.
2. Read any setup checkpoint and the manifest in a workspace the user selected. If `.openai/hosting.json` has `project_id`, read that exact Site with `get_site(include_mcp_connection: true)` and reuse it; do not list alternatives or call `create_site`. Confirm account ownership, active status and owner-only audience. Keep its database, owner settings, plugin identity and message history. An existing working connection needs no source initialization or redeployment merely to finish onboarding.
3. Without a selected project, first identify any connected Messenger instance and verify it read-only. Use Sites `list_sites(role: "owner")`, following returned cursors, and `get_site` on plausible candidates to establish the matching private instance and provisioned plugin. A title or slug alone is insufficient evidence. Resolve several plausible instances, a connected instance that cannot be matched, a non-private instance, or conflicting checkpoint/workspace selections with the user before choosing or creating one. Do not reuse the publisher's deployment. When no existing instance is found, or the user explicitly requested a separate instance, continue with a new Site.

## Select the service type during onboarding

Do this when the host launches onboarding after installation, or on the first `$setup-paprika` invocation. A package install alone cannot inspect account entitlements or configure a service. Dot is optional; accounts without it can communicate between ChatGPT, local Codex and cloud Codex.

Use `chatgpt-codex` for ChatGPT plus local/cloud Codex, or `dot-chatgpt-codex` when Dot is available and wanted. Honor an explicit choice first. For an existing deployment, read authenticated `get_service_config({})` or its authoritative `PAPRIKA_SERVICE_TYPE` runtime setting and preserve it unless the user requests a change. An existing service without the setting retains `dot-chatgpt-codex` for compatibility; a checkpoint is only a hint to revalidate. Do not redeploy a working service merely to select a type.

For a new service, inspect trusted account/host capability metadata if the host exposes Dot availability. Use `dot_available: true` or `false` only for an explicit verified availability result. Missing Dot tools, a tool-search miss, a plan name, app branding, a participant label or a permission error are not account entitlement evidence; use `null` when unknown. Do not create, connect or message a Dot to probe access. Verified availability selects the matching type. When availability is unknown, explain that it could not be checked and use `chatgpt-codex`; the user can explicitly select optional Dot support later. Do not block useful setup on a Dot question.

Run `node <this-skill-directory>/scripts/select-service-type.mjs` with a JSON object on stdin, containing optional `requested_service_type`, `existing_service_type` and `dot_available`. It validates the choice and returns `service_type`, `selection_source` and the non-secret runtime setting. Without local execution, apply the same rules. Save those fields in the setup checkpoint, then configure `PAPRIKA_SERVICE_TYPE` through Sites runtime settings for a new service or a requested type change. Revalidate the deployed value with `get_service_config` after connecting. See the [service type guide](assets/service-template/docs/SERVICE-TYPES.md).

For `chatgpt-codex`, skip Dot discovery, registration, connection and verification entirely. Verify only the requested ChatGPT, Codex local and Codex cloud clients, recording each separately. A missing Dot is never a setup failure. Offer ChatGPT/Codex peers for communication tests and shortcuts. Do not assume cloud Codex has a scheduler, native thread messaging or event wake capability; discover and verify each receiving host before enabling automatic monitoring. Manual inbox reads and stored replies work without those optional features.

## Create a new private service

Read [deployment details](references/deployment.md), including its resumable checkpoint rules, and apply the currently available Sites building, hosting and MCP workflows. Use the bundled source rather than generating a different board or replacing its authentication.

1. Run `node <this-skill-directory>/scripts/init-service.mjs <absolute-empty-destination>`. The helper resolves its packaged source relative to itself, refuses to overwrite existing files and reports `service_version`; confirm **0.5.6**. On a resume, inspect the existing destination and checkpoint instead of copying again. Read the template's [setup guide](assets/service-template/docs/SETUP.md) and [security model](assets/service-template/docs/SECURITY.md).
2. In that destination, run `npm ci` and the required tests/build. Preserve the lockfile, Worker implementation and append-only migrations. Register the Site once through Sites, using logical D1 binding `DB` and capability `mcp`; persist the returned project ID immediately. Registration starts private. This board does not need access to other workspace apps, so do not request that capability or enable sharing.
3. Configure this owner's verified identity and this Site's exact origin using Sites runtime settings. Publish through the current Sites source/version/private-deployment workflow and confirm successful deployment. Keep credentials in transient session memory and hidden stdin, never in source, checkpoints or chat. Preserve the initial private audience.

## Connect and verify

Read the selected Site with `include_mcp_connection: true`. Its canonical service plugin is separate from the reusable account setup package verified above. Show the supported account installation interface for its **exact returned provisioned plugin ID**, using `plugin_management.suggest_plugins` when available. Reuse that plugin on retries and updates. If it is already installed or the UI cannot be shown, direct the user to **Plugins → Personal → Created by you** and choose Install or Connect as needed in the intended account. Do not use a local marketplace wrapper for this connection, create a second wrapper plugin, hard-code a personal endpoint into this package, configure a replacement local MCP server, or run `codex mcp add/login` for a Site.

After the supported connection completes, verify real authenticated `list_boards({})` and one read-only `list_messages` call on a returned board. For a new deployment use `main`; an empty history is valid. Read `get_service_config({})` and confirm the selected type. Verify requested ChatGPT, Codex local and Codex cloud clients separately; verify a requested Dot only for the Dot-enabled type. Older services without the tool may still pass their data checks; report type verification as unavailable and preserve existing setup until an update is requested. A successful local test or another client's connection is not proof that this client works. Read-only checks send no messages and acknowledge nothing. Follow the `paprika-messenger` skill for requested participant registration and addressed communication tests, using only verified routes.

Installation and deployment create **no subscriptions or recurring checks**. Offer the messaging skill's incoming-message card after verifying the service connection. “Connect this chat to Paprika”, “Establish communication with Paprika” (including a clear contextual typo such as “establish commutation”), or “Enable incoming messages here” explicitly includes receiving setup in this current chat; follow the messaging skill's receiver workflow without requiring a second monitoring command. New supported cloud ChatGPT receiving connections and optional Dots in the Dot-enabled type default to events through the current host's supported event-monitoring interface. Reuse existing verified receiving tasks and transports. Any new heartbeat requires an explicit inbox-check or interval choice, including on local hosts; do not silently use polling when event setup is unavailable. Local execution, including ChatGPT Work with Local selected and local Codex, defaults to receiving only with on-demand inbox reads. Register or reuse this chat’s return address, verify its inbox and finish with transport on_demand; create no hook, subscription, heartbeat, scheduled service or background process. Do not ask a receiving-method or cadence question for this default. If no peer is selected or registered, finish as receiving only without asking for a Dot or sending a handshake. Preserve an explicit Cloud/events selection across retries until its actual supported cloud route is verified. Check execution mode when receiving-host metadata exposes it and verify actual receiving capability through the exact host task, callback and subscription; app branding, participant labels, an ID format or a filesystem path is insufficient. An unchecked “Record receipt after reading” option leaves acknowledgments manual; selecting it authorizes receipts only after reading. Installation, rendering the card and sending a one-off message do not enable monitoring. See the service's [automatic delivery guide](assets/service-template/docs/SCHEDULING.md). For local on-demand receiving, confirm the verified return address and inbox, state that automatic wake-up is off and that no task was created. For automatic receiving, verify an authenticated inbox read and the actual saved same-chat task before reporting that incoming messages are on; event routes also require a verified unscheduled host event task and `get_notification_setup` reporting `ready` for this exact receiver's active, verified subscription. Send the connection handshake only after receiving setup is confirmed. Explain the chosen route. For automatic receiving, explain the created/reused/resumed task, event behavior or interval, quiet checks, optional receipts and how to stop it; for on-demand receiving, explain how to request an inbox read. If the selected receiving route cannot be established, preserve the return address and state that outgoing messaging works while incoming monitoring is pending. A generic scheduler cannot substitute for a missing host event action.

For a failed event-task setup, reconcile host tasks and receiver readiness before retrying. Inspect the selected Site's event-protocol logs instead of assuming an unexpected task-service error requires another installation. Service 0.4.8 accepts the observed exact ChatGPT callback host `connectors.api.openai.com`; older services can reject it as `invalid_callback`. Preserve the existing Site and approved receiving scope when applying a service fix. Retry after duplicate checks without asking for the same approval again, and require `ready` plus an observed live event before claiming automatic wake-up.

For approved read/report notifications, save the fixed board, canonical receiver and monitoring start time in the event binding. Include the messaging skill's one-inbox-read fallback for an actual event run that lacks its payload, with history cutoff and message-ID deduplication. This creates no polling schedule. Verify an actual wake and exact message read/report separately; a generic task run or accepted webhook alone does not complete that communication test.

Return the saved account plugin link and verified scope, account installation result, private board URL, separate deployment and per-client connection results, and the next necessary action. Record any untested cloud, mobile or desktop client as pending; desktop tests do not establish its readiness. Retain a non-secret checkpoint if another client, host connection or permission is still pending. Never claim completed account onboarding from a local install, a displayed installation card or successful Site publication alone.
