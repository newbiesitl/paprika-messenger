Help the user obtain one working private communication service and verify each requested client. The package includes the messaging skill, this onboarding skill and the complete service source, version **0.5.4**, under `assets/service-template/`. It has no shared MCP endpoint. Each owner uses their own Site and database. Explicit user instructions take priority; if they request another hosting or identity design, resolve the source's Sites authentication requirement before deploying.

The manifest designates this skill for onboarding. A host may offer or launch it after installation; do not claim that every Install click automatically runs setup or deploys a server. If onboarding has not started, the user can ask to set up Paprika Messenger. Installing the package, publishing a Site, displaying an installation card, connecting a client and enabling recipient notifications are separate milestones.

Explain briefly that messages and routing data are stored in the owner's private service and are not sent to the package publisher. The bundled [privacy notice](../../PRIVACY.md) explains storage and deletion. Setup needs no transcripts, private message histories or pasted authentication secrets.

## Check access and find the right instance

1. Inspect available native capabilities before creating anything. A connected Messenger can be checked with read-only `list_boards` and `list_messages` calls. Sites setup needs native Sites discovery/metadata, registration, runtime-settings and publication capabilities, plus a writable execution environment with Node.js 24 or later. Search available tool/plugin metadata before reporting a missing capability. If Sites is missing or disconnected, discover the eligible Sites integration and show its supported Install/Connect interface; do not guess a plugin ID. If that interface is unavailable, direct the user to enable/connect Sites in the host's Plugins UI. Never silently change workspace administrator controls or treat a permission error as permission to bypass them. Continue independent inspection while a connection is pending; dependent Site operations wait for a real connection. For a restricted workspace or missing execution environment, state the specific prerequisite and retain completed setup.
2. Read any setup checkpoint and the manifest in a workspace the user selected. If `.openai/hosting.json` has `project_id`, read that exact Site with `get_site(include_mcp_connection: true)` and reuse it; do not list alternatives or call `create_site`. Confirm account ownership, active status and owner-only audience. Keep its database, owner settings, plugin identity and message history. An existing working connection needs no source initialization or redeployment merely to finish onboarding.
3. Without a selected project, first identify any connected Messenger instance and verify it read-only. Use Sites `list_sites(role: "owner")`, following returned cursors, and `get_site` on plausible candidates to establish the matching private instance and provisioned plugin. A title or slug alone is insufficient evidence. Resolve several plausible instances, a connected instance that cannot be matched, a non-private instance, or conflicting checkpoint/workspace selections with the user before choosing or creating one. Do not reuse the publisher's deployment. When no existing instance is found, or the user explicitly requested a separate instance, continue with a new Site.

## Create a new private service

Read [deployment details](references/deployment.md), including its resumable checkpoint rules, and apply the currently available Sites building, hosting and MCP workflows. Use the bundled source rather than generating a different board or replacing its authentication.

1. Run `node <this-skill-directory>/scripts/init-service.mjs <absolute-empty-destination>`. The helper resolves its packaged source relative to itself, refuses to overwrite existing files and reports `service_version`; confirm **0.5.4**. On a resume, inspect the existing destination and checkpoint instead of copying again. Read the template's [setup guide](assets/service-template/docs/SETUP.md) and [security model](assets/service-template/docs/SECURITY.md).
2. In that destination, run `npm ci` and the required tests/build. Preserve the lockfile, Worker implementation and append-only migrations. Register the Site once through Sites, using logical D1 binding `DB` and capability `mcp`; persist the returned project ID immediately. Registration starts private. This board does not need access to other workspace apps, so do not request that capability or enable sharing.
3. Configure this owner's verified identity and this Site's exact origin using Sites runtime settings. Publish through the current Sites source/version/private-deployment workflow and confirm successful deployment. Keep credentials in transient session memory and hidden stdin, never in source, checkpoints or chat. Preserve the initial private audience.

## Connect and verify

Read the selected Site with `include_mcp_connection: true`. Show the supported installation interface for its **exact returned provisioned plugin ID**, using `plugin_management.suggest_plugins` when available. Reuse that plugin on retries and updates. If it is already installed or the UI cannot be shown, direct the user to **Plugins → Personal → Created by you** and choose Install or Connect as needed. Do not create a second wrapper plugin, hard-code a personal endpoint into this package, configure a replacement local MCP server, or run `codex mcp add/login` for a Site.

After the supported connection completes, verify real authenticated `list_boards({})` and one read-only `list_messages` call on a returned board. For a new deployment use `main`; an empty history is valid. Check ChatGPT, Codex and the requested Dot separately when available, recording which client actually passed. A successful local test or another client's connection is not proof that this client works. Read-only checks send no messages and acknowledge nothing. Follow the `paprika-messenger` skill for requested participant registration and addressed communication tests, using only verified routes.

Installation and deployment create **no subscriptions or recurring checks**. Offer the messaging skill's incoming-message card after verifying the service connection. “Connect this chat to Paprika”, “Establish communication with Paprika” (including a clear contextual typo such as “establish commutation”), or “Enable incoming messages here” explicitly includes receiving setup in this current chat; follow the messaging skill's receiver workflow without requiring a second monitoring command. New ChatGPT receiving connections and Dots default to events through the current host's supported event-monitoring interface. Reuse existing verified receiving tasks and transports. Any new heartbeat requires an explicit inbox-check or interval choice, including on local hosts; do not silently use polling when event setup is unavailable. Local execution, including ChatGPT Work with Local selected and local Codex, has no event wake bridge in this workflow. Keep a new event connection pending and offer Cloud mode or explicitly selected heartbeat inbox checks; never create a new heartbeat automatically. Check execution mode when receiving-host metadata exposes it and verify actual receiving capability through the exact host task, callback and subscription; app branding, participant labels, an ID format or a filesystem path is insufficient. An unchecked “Record receipt after reading” option leaves acknowledgments manual; selecting it authorizes receipts only after reading. Installation, rendering the card and sending a one-off message do not enable monitoring. See the service's [automatic delivery guide](assets/service-template/docs/SCHEDULING.md). Verify an authenticated inbox read and the actual saved same-chat task before reporting that incoming messages are on; event routes also require a verified unscheduled host event task and `get_notification_setup` reporting `ready` for this exact receiver's active, verified subscription. Send the connection handshake only after receiving setup is confirmed. Always explain the created/reused/resumed task, event behavior or interval, quiet checks, optional receipts and how to stop it. If the selected receiving route cannot be established, preserve the return address and state that outgoing messaging works while incoming monitoring is pending. A generic scheduler cannot substitute for a missing host event action.

For a failed event-task setup, reconcile host tasks and receiver readiness before retrying. Inspect the selected Site's event-protocol logs instead of assuming an unexpected task-service error requires another installation. Service 0.4.8 accepts the observed exact ChatGPT callback host `connectors.api.openai.com`; older services can reject it as `invalid_callback`. Preserve the existing Site and approved receiving scope when applying a service fix. Retry after duplicate checks without asking for the same approval again, and require `ready` plus an observed live event before claiming automatic wake-up.

For approved read/report notifications, save the fixed board, canonical receiver and monitoring start time in the event binding. Include the messaging skill's one-inbox-read fallback for an actual event run that lacks its payload, with history cutoff and message-ID deduplication. This creates no polling schedule. Verify an actual wake and exact message read/report separately; a generic task run or accepted webhook alone does not complete that communication test.

Return the private board URL, separate deployment and client-connection results, and the next necessary action. Retain a non-secret checkpoint if another client, host connection or permission is still pending. Never claim completed onboarding from a displayed installation card alone.
