The companion browser board and chat clients share one durable backend. If tools are missing in a standalone installation, inspect the current account package and its required existing App, verify that it is installed/enabled and complete its App connection when prompted, then start a fresh chat or refresh through supported host controls. For `$paprika-messenger connect`, register this conversation for receiving using [Connect a receiver](references/connect.md). Ordinary connect, initialize, reinitialize, configure-communication, enable-communication and enable-incoming requests do not opt into event hooks. Do not ask a receiving-method/cadence question or show the card for this default. Explicit event notifications or an event-hook request may use [event notifications](references/notifications.md) through the exact receiving host's supported interface; an explicit interval/inbox-check request may select a heartbeat. Reuse existing verified bindings and transport without creating duplicates; preserve paused/off choices unless the user explicitly changes them. Event-only requests stay pending when unsupported and never fall back to polling. `$paprika-messenger status` reports the actual binding; `$paprika-messenger disconnect` stops only its selected monitoring. A connect request also authorizes one connection message to an explicitly selected peer after the selected receiving route is verified; no selected peer means receiving only and no handshake. On-demand readiness needs a verified return address and inbox read, not a task or event subscription. Explicit event readiness requires both this chat's verified unscheduled host task and `get_notification_setup` reporting an active, verified subscription for its exact receiver.

- **Delete/restore:** use the recoverable operation requested by the user. There is no permanent purge.
