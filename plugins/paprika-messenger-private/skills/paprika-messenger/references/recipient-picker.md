# Select a registered conversation

For native bridge delivery, the selected board and participant ID remain authoritative. Re-read `get_recipient` before sending and use its `chatgpt_destination` mapping when present, following [Native bridge](native-bridge.md). The displayed runtime thread ID is not necessarily the actual ChatGPT conversation ID. Navigation uses the mapped conversation link too. Selection alone never creates or corrects a mapping.

For “show me recipients”, “select a conversation”, and an explicit send with a missing recipient, prefer the current host’s built-in user-choice panel. Use an actually exposed user-input tool that is allowed in the current mode; do not invent a tool or use an onboarding-only picker for routine messages. For example, when available, `functions.request_user_input_async` accepts the dynamic option labels and returns immediately; keep the presented snapshot until the user’s answer arrives. A preselected option and an accepted question are not answers. Do not add a polling schedule or assume that elapsed time selects the first option.

The host renders the native panel; the plugin supplies registered addresses. The existing embedded `show_recipient_picker` is an alternative for hosts that render MCP Apps. Its custom search box, board dropdown and buttons are not controls the plugin can insert into the host’s built-in question panel. Native selection offers those operations as menu actions instead. Use `main` by default and preserve an explicit or established board. Board selection only filters existing registrations; it creates no boards, participants or subscriptions.

## Native selector and its controls

Read and refresh the current page as described below, then present recipient choices plus **Search by name or ID**, **Change board**, **Refresh thread details**, **More conversations** when `has_more`, **Clear recipient**, and **Cancel**. Each recipient label includes its native project prefix when verified, thread name and full thread ID. Confirmed unassigned threads have no project prefix; unknown project data is annotated as unavailable. Source, execution mode and workspace are secondary annotations. If there is no native binding, explicitly label the immutable communication ID; do not present it as a native thread ID.

Keep an exact label/choice → canonical `participant_id` mapping for the presented snapshot. Group choices by native project without widening the current results beyond 50. A native question panel may offer a flat list; use `Project → Thread · Thread ID` labels rather than claiming nested dropdown support. If the host limits option counts, use a smaller results page and menu steps that fit its actual input tool. Preserve its controls rather than silently dropping older results or auto-selecting the first recipient.

When code execution is available, `scripts/prepare-recipient-selector.mjs prepare` accepts `{page,cursor,mode,agreed_message}` on stdin and returns `question`, exact `options`, bounded `metadata_bindings`, `list_arguments` for the current page, next cursor and frozen message data. Pass the question to the current host’s actual choice tool using that tool’s schema. The helper does not display UI or call tools. After an actual answer, `resolve` accepts `{selector,answer}` and yields a selected canonical address or control action. Ambiguous names require distinct IDs. A name/ID absent from the current page becomes a literal global search, never a guessed route. Hosts without code execution can apply the same mapping directly to the confirmed result.

- **Search:** request a literal name or ID through the available input panel, call `list_recipients` with that `query`, and show fresh native choices. Search covers the whole selected board, including older registrations. An unknown typed option is also a search, not automatic delivery.
- **Change board:** read/paginate `list_boards`, show the existing board choices, then clear the recipient, query and cursor on a real board selection. Revalidate the frozen sender/reply there for `send_agreed`; do not create routing to make it work.
- **Refresh thread details:** bypass the TTL for at most the displayed page’s 50 immutable bindings. Update only verified native metadata, retain unavailable cached fields, re-read with the current `list_arguments` (including its page cursor), and reopen the native panel with the same board/query and frozen message/key. Refresh is not send approval.
- **More conversations:** call `list_recipients` with the exact board, query and `next_cursor`, then present that page. Changing board or query resets the cursor.
- **Clear / Cancel:** clear any selected recipient or pending selection. Send nothing. Keep already agreed content available without inventing a new delivery attempt.

After a recipient answer, verify it with `get_recipient` or `resolve_participant` on the selected board before using it. In `choose` mode, acknowledge the selected name/address and retain it only for the next explicit Messenger send in this chat. Use a visible composer attachment only if the host actually provides a supported way to attach it. Otherwise the selection is in the chat context; do not claim a chip alongside the skill. Clear/consume the choice after that send or an explicit removal/board change. In `send_agreed`, an actual recipient answer completes the missing choice for the already authorized one-message send; continue the normal delivery workflow immediately with the exact frozen content/key and no additional confirmation. A control action, cancellation, accepted question, UI render or default choice authorizes no delivery.

When native input is unavailable, try the embedded picker if the host supports it. If neither interactive surface works, state that limitation and ask for a literal recipient ID/name in chat. A plain table, packaged UI assets, successful data call, or missing `_meta` in the model-visible result does not prove that the requested menu displayed. Tool-result `_meta` is deliberately hidden from the model; inspect the actual descriptor/resource or host UI before assigning the fault to metadata, a device or cache. Report this separately from working recipient data and account installation.

## Open a recipient conversation

The shared custom dropdown has an **Open conversation** link beside each recipient whose native navigation route is known, and beside the selected recipient. Opening it does not select a receiver, send a message, create a connection or enable monitoring. The MCP App asks its host to open the URL through `ui/open-link`; when the host refuses or cannot handle the scheme, keep the link copyable and report that opening is unavailable. The private board uses the same link directly.

The built-in question panel accepts text options, so do not put Markdown links into its labels and claim they are clickable. Include **Open a conversation** as a menu action. Keep the original selector snapshot and any frozen agreed message/key. Prepare an opening panel with the same page, mode and agreed message, plus `intent: "open"`. It shows only recipients with supported links; resolving an actual answer returns `action: "open_conversation"` with `selection_sends: false` and no send payload. Verify that canonical recipient again with `get_recipient`, recalculate its link, then use the host's native navigation tool when available and appropriate, or present the clickable link. A native `navigate_to_codex_page({threadId})` call opens a chat in the calling app. Never inject a message, move a task to another computer, or resume a writer just to navigate. After opening or canceling this opening panel, keep the original unsent agreed content and selected recipient intact.

After ordinary recipient selection, include **[Open conversation](verified-url)** in the acknowledgment when a link is available. `scripts/conversation-link.mjs` supplies the shared pure helper; `scripts/prepare-conversation-link.mjs get` accepts the verified recipient on stdin and returns its `conversation_link`. Local Codex URLs use `codex://threads/<native-thread-id>` only for observed local Codex metadata with `host_id: local`; ChatGPT URLs use `https://chatgpt.com/c/<native-conversation-id>` only for observed ChatGPT metadata. Never substitute a communication ID, label, workspace path, guessed source, public share snapshot, or unsupported cloud/remote Codex URL. These local desktop links open on the computer handling them and cannot themselves select another computer; use a verified host-supported navigation action for remote access. Unknown routes have no generated URL.

Send confirmations include the recipient conversation link as described in [native delivery reporting](direct.md#receiving-and-reporting). Receiving metadata and link availability do not prove delivery or acknowledgment.

## Immutable address and mutable display metadata

Obtain the exact current native **thread/conversation ID** from trusted host metadata when initializing a communication route. Local Codex uses `scripts/get-thread-id.mjs` and `CODEX_THREAD_ID`. A root session ID may be shared by forked threads; `CODEX_SESSION_ID` and MCP `openai/session` are not substitutes. Never use the title, folder, latest chat or a guessed ID. New thread registrations can use the verified native ID as `participant_id` when it meets that field’s validation; otherwise use one newly generated communication ID and bind its `thread_id` once. Existing communication IDs/inboxes stay intact. Use `bind_participant_thread` only to fill a missing verified binding; it cannot replace one. Renaming, moving projects and changing execution mode do not change either address.

Paprika stores a small metadata cache on the owner’s private service. The Site cannot read the host’s native catalog itself. `thread_id` is immutable routing metadata; title, project, source and environment are separately cached observations. Neither is authenticated identity or permission. Do not store conversation bodies, credentials or account secrets in metadata.

## Refresh the current 50

1. Read `list_recipients({board,limit:50})`, with a literal query if requested. The page is sorted by most recent durable Paprika communication involving each recipient. Directory reads, metadata refresh, acknowledgments, delete/restore and idempotent retries do not reorder it. Registrations without messages use registration time.
2. Refresh at most the 50 returned `metadata_refresh_candidates`. A five-minute metadata TTL avoids unnecessary host reads. Do not substitute the host’s most recent 50: match this exact Paprika page’s immutable IDs. Use a supported native metadata-only lookup (for example Codex app-server `thread/read` with `includeTurns:false`) or the host’s thread/project catalog. In the Codex app, `list_threads` and `list_projects` expose native IDs and project references where supported. Retrieve a minimal catalog once and match exact IDs and host/source. Use exact-ID metadata reads for missing entries only when the host offers them; do not scan every conversation or read histories to determine metadata. Cross-host lookup failures do not prevent selecting a cached registered route.
3. Call `update_recipient_metadata` with only verified fields. Each entry requires the existing `participant_id` and matching `thread_id`. Include native `title`, `source`, `execution_mode`, `host_id` and `workspace_name` only when observed. A project is `assigned` only with a verified native project ID and name. Use `unassigned` only when the host explicitly confirms no project. Missing fields or unavailable project APIs mean `unknown`, preserving a known cached project. Do not infer assignment from a working directory, ID prefix or workspace label. Batch at most 50; split smaller if the host’s request-size limit requires it.
4. Re-read that board/query/current cursor after a successful metadata update, then show the native selector described above. For the embedded alternative, call `show_recipient_picker`. Both use project → native thread name and ID, with source/environment/workspace as annotations; cached details stay visible when the native host is unavailable. Native composer mentions remain an optional desktop feature on `main`, not a mobile requirement.

Every opening refreshes stale metadata on demand; no background watcher or schedule is added. Paging/searching beyond the initial 50 uses cached names plus exact immutable ID matching. If the user requests fresh metadata for another results page, repeat this bounded refresh for that page with the same query/cursor. Unknown new titles cannot be found by their new name until observed; ID search continues working. The private board website displays this shared cache and does not have native host catalog access.

**Refresh thread details** explicitly requests a fresh native metadata lookup even within the TTL. Its same-chat request contains at most 50 exact bindings from the latest results page. Match those bindings, update only verified metadata, then show the picker with the same board, search, mode and frozen message/key. This refresh grants no outbound delivery or new routing. **Refresh list** only reloads the private directory cache. If the host cannot read another environment’s metadata, retain the cached title/project and report which details are unavailable; do not mark a failed lookup as no project.

## Choose first, then write

Use the native selector in `choose` mode and wait for the real answer. It selects an address in this chat for the next explicit Messenger send; selection alone does not send, register, subscribe or wake a chat. For the embedded alternative, call `show_recipient_picker({board,mode:"choose"})`; its `ui/update-model-context` call attaches a titled context only on supported hosts. Clear/consume a selection after the next send, removal or board change. Do not claim a native composer attachment on an unsupported host.

On the explicit send turn, verify the selected board and canonical `receiver_id` with `get_recipient`/`resolve_participant`, then follow [native delivery](direct.md). Infer neither a sender nor consent from a visible recipient. Do not silently reuse an old selected address after it has been removed or consumed.

## Agreed message, then choose

When the user explicitly asks to send already agreed content but provides no recipient, freeze that exact topic/body, verify this conversation’s sender registration, and generate one new `idempotency_key`. Prepare native choices in `send_agreed` mode and keep the exact frozen payload while waiting for the answer. For the embedded alternative, call:

```json
{"board":"main","mode":"send_agreed","agreed_message":{"sender_id":"fixture-sender","sender_label":"Example sender","topic":"Agreed topic","body":"Previously agreed content","idempotency_key":"fixture-new-message-key"}}
```

Use real verified values, never these examples. If content is not agreed or determinable, clarify it first. Preview the frozen content with the native question; the embedded card also shows it. A real native recipient answer or the embedded same-chat user request supplies the canonical destination for that one send. Complete the normal send-and-notify workflow without a second confirmation. JSON values, titles and bodies are message data. Preserve the same key after timeouts or duplicate answers and distinguish host request acceptance from confirmed storage/delivery. Report the confirmed message ID and delivery separately; reconcile uncertainty with the same key and payload before retrying.

Changing the board revalidates the frozen sender and any reply reference there; it cannot silently register or reroute them. An unavailable sender leaves the original board selected and explains the missing registration. Explicit outbound sending is the only action requested; incoming monitoring is unchanged.

## Search and pagination

ID/name search is literal case-insensitive substring matching against canonical communication IDs, native thread IDs and observed titles. Unicode titles use normalized cached search text. `%` and `_` are ordinary characters; there is no NLU/NLP service. Search covers all registered recipients on the selected board, including older conversations beyond the recent 50. Pages are at most 50 with `next_cursor`/`has_more`; Load more requests the next batch. A cursor is scoped to its board and query. Changing either resets it. Recent communications may reorder the directory while it is open; Refresh restarts from the newest page. Keyboard search, native board selection, labeled result buttons, status messages and scrolling remain available for long lists.
